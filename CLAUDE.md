# AI Engineer Roadmap — project guide

A personal 24-week "AI Engineer Roadmap" tracker: Next.js (App Router) + TypeScript (strict) + Tailwind CSS.
**No backend.** Progress lives in the browser's `localStorage` and can be exported/imported as JSON.
**All roadmap content is typed data in `src/data/`**, kept separate from UI so content can be edited without touching components.

> Build status: stages 1–3 of 6 done (scaffold, data layer + logic, app shell + dashboard / this week / timeline / all tasks / settings). Still to come: projects, stack pages, learn-vs-delegate and the DSA tracker (stage 4); weeks 3–24 and projects 2–5 (stages 4–5); final docs and hardening (stage 6). Sections marked _(planned)_ describe that later work — update this file as each stage lands.

## Commands

| Command | What it does |
|---|---|
| `npm run dev` | Dev server on http://localhost:3000 |
| `npm run build` / `npm start` | Production build / serve it |
| `npm run lint` | ESLint (Next config + the layering rules below) |
| `npm run typecheck` | `next typegen`, then `tsc --noEmit` |
| `npm test` / `npm run test:watch` | Vitest: unit tests for `src/lib` and the content validator for `src/data` |
| `npm run validate:content` | Only the content validator (run it after editing `src/data`) |
| `npm run check:links` | Fetches every URL in `src/data` and reports broken or moved ones |

"Done" means `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` all pass with no errors.

## Structure

```
src/
  app/                 routes: thin, they pick data and render components
  components/          layout/ ui/ dashboard/ week/ timeline/ tasks/ settings/  (small, one component per file)
  hooks/               React adapters: useAppState (the store), useSchedule, useProgress, useTheme, useHydrated, useToday
  lib/                 pure logic with *.test.ts beside each file
    state/             persisted-state types, parser, migrations, storage, transitions, store, export/import
  data/                ALL roadmap content (typed, no React): constants.ts, ids.ts, types.ts, helpers.ts, resources.ts,
                       tracks.ts, phases.ts, dsa-patterns.ts, weeks/, projects/, stacks/, learn-vs-delegate.ts
scripts/check-links.mjs
```

Routes: `/` dashboard · `/week` (current week) · `/week/[n]` · `/timeline` · `/tasks` (all tasks, filters in the URL) · `/settings`.

## Architecture rules (ESLint enforces the import ones)

Dependencies point inward: `app/`, `components/`, `hooks/` → `lib/` → `data/`.

- `src/data/**` — plain typed content. **No React/Next imports and no imports from `src/lib`.**
- `src/lib/**` — pure, framework-free logic. **No React/Next.** Every module has a `*.test.ts` beside it.
- `src/hooks/**` — the only place React state meets the store (`useSyncExternalStore`).
- `src/components/**` — presentational and small (aim ≲120 lines, one component per file, typed props). No content literals inside components.
- `src/app/**` — thin routes: pick data, render components.
- Client components import `@/lib/content` (the resolved weeks/phases/tracks) rather than `@/data`, so routes do not ship project or stack content they never show. Pass project/stack data from server pages as props.

## Next.js 16 notes

- `params` and `searchParams` are Promises. Type them with the global `PageProps<'/route'>` / `LayoutProps<'/route'>` helpers (generated by `next typegen`), or `{ params: Promise<{ … }> }`.
- Dynamic routes are prerendered with `generateStaticParams`; `dynamicParams = false` where the set is closed (e.g. only weeks that exist in `src/data/weeks`).
- A client component that calls `useSearchParams` must sit inside a `<Suspense>` boundary or the production build fails (see `app/tasks/page.tsx`).
- Always check `node_modules/next/dist/docs/` for the installed version before using a Next API from memory.

## State and hydration rules

- One versioned localStorage key (`air:v1`; `air:v1:backup` holds the one-step undo, `air:v1:corrupt` any unreadable data kept for recovery). The theme preference is separate (`air:theme`) and not part of exports.
- The store in `src/lib/state/store.ts` is framework-free; `src/hooks/useAppState.ts` adapts it with `useSyncExternalStore`. On the server and during hydration it returns an empty default state, so server and client HTML match.
- **Never render anything that depends on saved progress, the start date or "today" differently on the server.** Gate it with `useHydrated()` / `useToday()` / `useSchedule().ready` and show a skeleton or omit the value (dates!). Static content (titles, task text, resources) renders normally.
- Dates are **local** `YYYY-MM-DD` strings (not UTC), so "today" and streaks do not shift around midnight. Use the helpers in `src/lib/dates.ts`.
- Changing the persisted shape: bump `SCHEMA_VERSION` in `src/lib/state/types.ts`, add a migration in `migrate.ts`, extend `parse-state.ts` and its tests. Imports of newer-schema files are refused with a clear message.

## Content rules

- Task ids are stable and globally unique (lowercase letters, digits, hyphens; convention `wNN-short-name`). Progress is keyed by them. **Never rename an id** after you have started ticking things off — add a new task instead.
- Estimated hours are derived, not typed. Each task has a relative `weight` (default 1); a track's hours for the week (`PLAN.weeklyHours` × its share in `PLAN.split`, rounded to the 15-minute `hourStep`) are split between that week's tasks by weight, always adding up exactly. At the default budget, weights written as hours (summing to 6.75 / 1.5 / 3 / 1.5 / 2.25 per track) map 1:1. DSA session tasks are generated with weight 1 each.
- Every task has 1–2 resources, official docs first. **Never invent a URL**: if you cannot confirm a link, omit `url` (the UI then shows the name with a "verify link" badge). Reusable links live in `src/data/resources.ts` (`R.someKey`).
- Do not hard-code version numbers or API details for fast-moving tech (MCP, Microsoft Agent Framework, AI SDK, coding-agent features). Link to the official docs hub (e.g. the MCP `…/specification/latest`) and add "check the changelog" tasks.
- Use synthetic data in every project description — never real client data.

## How to add or edit content

After any edit run `npm run validate:content` (it catches duplicate ids, missing resources, bad URLs, unknown DSA problem names, weeks that do not match the time budget, broken references), and `npm run check:links` after touching URLs. `leetcode.com` is bot-blocked and shows as "blocked" — expected.

- **Time budget**: edit `PLAN` in `src/data/constants.ts` (weekly hours, track split, DSA sessions per week, mock-week interval). Every estimate rescales.
- **A task**: add `ai(...)`, `assisted(...)`, `design(...)` or `fundamentals(...)` (from `data/helpers.ts`) to the week's `tasks` array: `ai("w03-streaming-ui", "Title", { detail, weight, resources: [R.x, R.y], projectId })`.
- **DSA sessions**: set the week's `dsa: patternWeek("arrays-hashing", [[problem names for session 1], [session 2], [session 3]])` using exact names from `dsa-patterns.ts`, or `mockWeek([...pattern ids])` for mock-interview weeks (6, 12, 18, 24). `defineWeek` generates the session tasks.
- **A week**: copy an existing `src/data/weeks/week-NN.ts`, change `number`, `phaseId`, text and tasks, then add it to `src/data/weeks/index.ts`. `/week/NN`, the timeline and the progress maths pick it up automatically.
- **A resource**: add an entry to `R` in `resources.ts` (or inline `{ title, url }` in a task). Run `npm run check:links`.
- **Tracks / phases / DSA patterns**: `tracks.ts`, `phases.ts`, `dsa-patterns.ts`. New closed ids (a project, a stack page, a DSA pattern) also go in `ids.ts`; project titles live in `PROJECT_TITLES` there.
- _(planned: projects, stack topics, learn-vs-delegate cards — documented when stage 4 lands.)_

`src/lib/validate-content.test.ts` currently passes `allowPartialPlan: true` because weeks 3–24 and some projects are not written yet. **Remove that option in stage 5** so a missing week fails the build.

## Known environment notes

- `npm audit` reports high-severity advisories inside the **dev-only** lint toolchain (`braces` → `fast-glob` → `eslint-config-next`). Nothing ships to the browser; `npm audit fix --force` would downgrade `eslint-config-next`, so do not run it.
- ESLint is pinned to v9 because the React/import plugins bundled with `eslint-config-next` do not support v10 yet (npm prints a deprecation notice for 9.x — expected).
- Vitest is pinned to v4: Vitest 5 does not list Node 25 as supported, and this machine runs Node 25.
- `.claude/launch.json` defines the `dev` server (port 3100) used for in-app browser previews.
